# Architectural & Business Decisions

Chronological. Each entry: the decision, why, and its impact.

---

**One shared `asset_ledger` for every unit, regardless of how it entered the system.**
Why: the app previously ran two disconnected purchasing pipelines (legacy `purchases` table vs. `purchase_orders`/`purchase_order_items`/`purchase_order_asset_mapping`), neither of which supported grading/QC, warranty, RMA, or sale-time stock decrement. Rather than build those features twice, `purchase_order_asset_mapping` was renamed to `asset_ledger` and extended with provenance (`source`), grading, warranty, and sale-linkage columns; both entry doors write into it.
Impact: every downstream feature (QC, sale, repair, RMA) is built once against one table. A `source` column (`purchase_order` / `legacy_purchase` / `employee_intake`) preserves where each row came from.

---

**API-layer role enforcement, not RLS, not middleware.**
Why: almost every existing route already used the Supabase service-role client (`supabaseAdmin`), which bypasses RLS entirely — so tightening RLS policies would not have closed the actual exposure. There is also no `middleware.ts` in this app.
Impact: `lib/auth/session.ts` resolves the caller's role from the Bearer token (or cookie, for server components) inside each route handler; `lib/auth/redact.ts` strips sensitive fields from responses. Page-level guards (`RequireOwner`) exist for UX only and must never be treated as the real boundary.

---

**Employee-facing routes are secure by construction, not by retrofit.**
Why: retrofitting redaction onto every existing route is repetitive and easy to miss on a new route. New routes built for the employee-facing system are written to never `.select()` sensitive columns for a given code path in the first place.
Impact: `lib/auth/redact.ts`'s field-stripping approach is reserved for existing/legacy routes; new routes should design their query to not fetch what they don't need to return.

---

**Employee entries are immediately real; the owner's job is deferred paperwork, tracked by derived flags.**
Why: the owner initially asked for a two-stage capture → owner-approves model (Part 5 of the plan), then reversed this after using it — an approval gate meant stock/sold lists weren't trustworthy for real-time warranty lookups, and it put the owner in the middle of every transaction. The revised principle: an employee's action (stock in, stock out) is true the moment it happens; the owner does bookkeeping (PO, invoice) later, whenever they get to it.
Impact: intake writes a live `stock_movements` receipt and `asset_ledger` row immediately; sales write `status='sold'` and the stock/accessory decrement immediately; a repair "replacement" swap marks the given-out unit `sold` immediately. None of these wait for an owner action. "Has paperwork been done?" is always computed from existing relationships (`asset_ledger.po_id IS NULL`, `sales.finalized`), never a separate boolean — a separate flag can silently drift from what's actually true; a derived one cannot.

---

**Asset numbers are a Purchase-Order artifact, not an inventory-existence requirement.**
Why: numbering happens through an atomic sequence (`reserve_assets()` RPC) specifically because numbers are meant to correspond to a committed purchase — minting one for an employee's unreviewed intake entry (an earlier iteration of this design briefly did this) wastes numbers on units that might later turn out to be duplicates, mistakes, or otherwise never actually purchased through a real PO. Separately, the owner pointed out that QC and purchase-paperwork happen on independent schedules — a unit can be sold before the owner ever gets around to its PO.
Impact: `asset_ledger.asset_number` stays `NULL` from intake through QC through sale — identification during that whole window is by `serial_number` + row id. `POST /api/purchase-orders/from-intake` is the only code path that ever calls `reserve_assets()` for these units, and it accepts units in *any* status (including already-`sold`), because attaching purchase paperwork must never be blocked by, or itself block, the unit's operational lifecycle.

---

**Live Stock (employee-facing) and Stock/Main ERP (owner's historical reconciliation) are the same table, deliberately shown as two non-overlapping views.**
Why: the owner is manually reconciling a large backlog of historical/legacy stock data separately from day-to-day new-stock operations, and asked for these to be kept apart so neither activity confuses or interferes with the other — "connecting" them is a deliberate future step, not automatic.
Impact: both views query `asset_ledger` filtered by `source` (`=employee_intake` vs `!=employee_intake`) rather than living in separate tables — reconciling them later is a matter of removing a filter, not running a data migration. Implemented as one parameterized component (`components/StockView.tsx`) mounted at two routes, not two forked copies.

---

**`sold_by` is a plain owner-curated name, not a login-account foreign key.**
Why: incentive/commission attribution needs to work for staff who may not have (or may share) a login account, and shouldn't be forced to match whoever happened to be logged in when a sale was typed up.
Impact: `sales.sold_by` was migrated from `uuid references auth.users(id)` to plain `text`, sourced from the existing generic `custom_options` dropdown system (`category='staff_names'`) rather than a new staff table — reusing infrastructure already built for CPU/RAM/storage dropdowns.

---

**"Received Into" (payment account) is independent of "Sale Type" (GST/Cash).**
Why: which of the business's two accounts (or cash) received a payment is an orthogonal fact to whether the sale itself was invoiced as GST or cash — a GST sale can still be paid into either account.
Impact: `sales.payment_account` and `repair_jobs.payment_account` are separate columns from `sale_type`, both free values from a fixed set (`Digitalbluez`/`Techtenth`/`Cash`), not derived from or coupled to the GST/Cash distinction.

---

**Payment tracking uses amount-paid vs. balance-due, not a binary flag.**
Why: real sales include partial payments/deposits, not just "paid" or "not paid."
Impact: `sales.payment_status` (`pending`/`partial`/`paid`) plus `amount_paid` (numeric); balance due is computed (`sale_total - amount_paid`), never stored, avoiding a second value that could disagree with the first two.

---

**Standalone "Owner Review" queue page removed in favor of in-context actions.**
Why: a separate queue page duplicated information already visible in the Stock pages and felt like unnecessary extra navigation; the owner preferred working directly in the same lists.
Impact: "needs PO"/"needs invoice" surfaced as inline flags + a count banner on the Stock pages themselves (owner-only columns/actions on the same table employees use); the two leftover categories that didn't have a natural home (pending accessory types, open repair jobs) got their own small list pages instead of a shared queue.

---

**No dummy/placeholder purchase invoices, ever.**
Why: 751 historically-migrated Purchase Orders have no linked invoice at all. Creating a PI is already fully decoupled from PO creation time in the schema (`POST /api/purchase-invoices` just needs an existing `po_id`), so there's no technical reason to fabricate a placeholder — whenever a real invoice surfaces (even years later), it's just one real PI creation, same as for a brand-new purchase.
Impact: those 751 POs stay `po_status='received'` with no invoice indefinitely; this is a bookkeeping backlog item, not a blocker on anything operational (a unit with no PI is still fully sellable/gradeable).

---

**Legacy quick-entry customer/vendor CRM forms are not touched by the new quick-entry flows.**
Why: `AddCustomerDialog.tsx` (full CRM form, GST fields, marketing-source tracking) is still needed as-is on the main Customers management page; the Sell/Service quick-entry screens needed a much lighter version and editing the shared component in place would have added noise to the main CRM page's field set for no benefit there.
Impact: a separate `QuickAddCustomerDialog.tsx` (name/type/phone/email/address only) was built for Sell/Service instead of modifying the shared one — two components, not one component with conditional complexity. Later revised (2026-07-22): Has GST / GST Number were added back conditionally (only when type=Business) after the owner hit this gap selling to a business customer — GST is needed for that customer type specifically, not for the lightweight default (Individual).

---

**Asset-number reconciliation must be numeric/format-aware, not lexicographic.**
Why: two admin tools (`app/api/settings/asset-counters/route.ts`, and formerly a step in PO hard-delete) found "the current max asset number for a prefix" via `.order('asset_number', desc).limit(1)` — a plain string sort. Once old-format numbers (`DBAS682`, no year) and new-format numbers (`DBAS26-699`, with year) coexist under the same prefix, string order can rank the old one higher (`'6' > '2'` at the first differing character), silently resetting the counter to the wrong value. This is what let a real PO's numbering jump from the last real unit (`DBAS682`) to `DBAS26-699` instead of continuing at 683 — an earlier reservation had already run ahead due to this exact bug plus an unrelated non-transactional reserve-then-write gap in PO submission (still open, see below).
Impact: both reconciliation tools now filter candidates to `^PREFIX\d{2}-\d+$` matching the target year, then compare the extracted integer — never a raw string sort. PO hard-delete's equivalent step was removed outright rather than fixed (see next entry).

---

**PO hard-delete no longer tries to "recover" reserved asset numbers on delete.**
Why: recalculating the counter back down when a PO is deleted actively fights this project's own numbering design (`reserve_assets()` is an atomic, never-reused sequence — a cancelled purchase's numbers are meant to just be spent, not clawed back) and was the concrete source of the lexicographic-sort bug above.
Impact: `app/api/purchase-orders/[id]/hard-delete/route.ts` no longer touches `asset_counters` at all. Deleting a PO leaves the counter wherever it is — a small, permanent gap, which is the accepted behavior per the original numbering ADR, not a bug to re-introduce a fix for.

---

**Legacy (pre-2026) asset numbers were renamed to match the current format.**
Why: 697 legacy `asset_ledger` rows used old, inconsistent formats (`DBAS0001`-`DBAS682`, `C0001`-`C0024` — an even older Cash prefix predating today's `CSAS` — `SHIS1`, and 2 malformed numbers). The owner asked for these aligned to the current `PREFIX<YY>-<seq>` format rather than left as permanent legacy noise, accepting the risk that these numbers may already be on physical tags/old invoices.
Impact: each row was renamed using its *real* historical purchase year (from its linked PO's `po_date` — the 2026-05-15 bulk-migration timestamp on the rows themselves is unrelated to when units were actually purchased), sequenced chronologically within each (prefix, year) bucket. The original number is preserved in a new `asset_ledger.legacy_asset_number` column specifically so a physical tag or an already-issued document can still be cross-referenced after the rename. `asset_counters` was corrected to match. Verified zero collisions and zero remaining old-format rows before considering this done.

---

**Reassigning a unit's SKU is open to both roles; editing SKU master specs stays owner-only.**
Why: correcting which SKU an asset is linked to (a data-entry mistake, or a physical upgrade discovered at sale time) never reads or writes cost/vendor data — unlike editing a SKU's own specifications in `sku_master`, which does. Restricting reassignment to the owner would have forced every employee who notices a wrong/upgraded unit at the point of sale to interrupt the owner instead of just fixing it.
Impact: `PATCH /api/asset-ledger/[id]/reassign-sku` requires only a valid session, not `isOwner`. `PUT /api/sku-master/[id]` (editing specs) remains owner-gated. The Stock view's "Fix SKU" button stays owner-only by UI choice (a power-user correction tool), while the Sell form's "Change SKU" (same underlying dialog, `components/FixSkuDialog.tsx`) is shown to both roles — the permission boundary lives in the route, not the button.

---

**Cost of upgrading a specific unit before resale is an append-only ledger, not a single field.**
Why: a unit's `cost_price` is set once at purchase time; there was no way to record that a specific unit later had money spent on it (added RAM, a bigger SSD) before resale, which matters for accurate margin. A single overwritable "extra cost" field would lose history if a unit is upgraded more than once and can't say who added what or when.
Impact: new `asset_cost_adjustments` table (`asset_id`, `amount`, `reason`, `added_by`, `created_at`) — same idiom as `stock_movements`/`asset_qc_checks` elsewhere in this codebase. Owner-only end to end (`GET`/`POST /api/asset-ledger/[id]/cost-adjustments`, optionally filled in from the Fix-SKU dialog at the moment of a reassignment, or anytime from the asset detail page's Cost Adjustments panel) — employees never see or set it, consistent with cost/vendor redaction everywhere else.

---

**RAM/SSD spec entry moved from free-typed number+regex to a `custom_options` dropdown; combined configs are their own atomic entries, not parsed.**
Why: `SkuFormModal` and `AddPurchaseDialog` typed RAM/SSD as plain numbers with a regex-normalization rule (`(\d+)` — extract the first number). That rule silently collapsed any combined-module string (e.g. "8GB + 8GB") down to "8", making a dual-8GB unit indistinguishable from a genuine single-8GB unit in SKU-variant matching. Once entry is dropdown-only, the regex extraction became unnecessary *and* actively harmful.
Impact: RAM/SSD/Storage fields switched to `text` + `custom_options`-backed `SearchableSelect` (same pattern already used correctly in Stock Intake), with the regex-normalization rule removed entirely rather than replaced — `normalizeSpecifications` already no-ops safely when no rule is present. A combined configuration is added as its own literal `custom_options` value (e.g. `"8GB + 8GB (16GB)"`) alongside the atomic ones, so it compares as a fully distinct string with zero parsing logic. Existing catalog data was migrated from bare numbers to the matching canonical strings so old and new entries keep resolving to the same SKU variants.

---

**The ERP replaces Zoho as the official GST invoicing system — numbering must continue Zoho's legal series unbroken, not restart.**
Why: switching invoicing tools mid-financial-year is only safe if the new tool's invoice numbers pick up exactly where the old one's left off (Zoho was at `DBI2026/27-00680`) — a gap or a restart-at-1 would be a real bookkeeping problem, not cosmetic.
Impact: a new atomic `next_document_number(entity_key, doc_type, financial_year)` RPC (backed by `invoice_sequences` keyed on entity+doc_type+FY) replaces both the old racy MAX-scan numbering and a separate atomic-but-single-purpose RPC. Digitalbluez's real sales-invoice counter was seeded at `last_number=680`, verified live to still be exactly 680 after all subsequent testing (tests deliberately used the Techtenth/proforma/quotation series instead, which share no counter with the real Digitalbluez sales-invoice series, specifically so testing could never accidentally spend a real legal invoice number).

---

**Business entities (Digitalbluez/Techtenth/Cash) are configurable profiles, not hardcoded identities scattered across PDF generators.**
Why: before this, three separate PDF generators each hardcoded a *different wrong* company identity (one said "Digital Bluez" with a placeholder GSTIN, another said Bengaluru/Karnataka). None matched the real business. Techtenth and Cash also have no GST registration, which no part of the old system understood — invoices for those entities need to be a GST-free "Bill of Supply," not a tax invoice.
Impact: one `business_profiles` table (`key`, `legal_name`, `address`, `state`/`state_code`, `gstin`, `is_gst_registered`, `logo_url`/`signature_url`/`stamp_url`, `bank_details`, per-doc-type numbering prefixes) drives one shared PDF renderer, GST classification, and numbering — managed by the owner in Settings, not hardcoded in code. `sales.payment_account` (already existing, tracking which account received payment) is reused as the entity signal for `finalize`, rather than adding a new column.

---

**Quotation/Proforma line items reference a SKU, not a specific physical unit — conversion always routes through the normal Sell flow, never creates a sale/invoice directly.**
Why: refurb units are qty-1 and unique (no two are identical). Locking a specific serial number into a quotation at quote time would strand that unit from other buyers if the quote is never accepted. Separately, duplicating the sale-creation/invoicing logic inside the quotation system would create a second place that could disagree with the first.
Impact: `sales_document_items` stores `sku_id`/`accessory_id` + qty/rate/GST, not `asset_ledger_id`. "Converting" a line opens `/dashboard/entry/sell` with the customer and price pre-filled via query params; the owner still picks the actual unit there, going through the exact same `POST /api/sales-entry` every other sale uses. `sales-entry` accepts an optional `source_document_item_id` and marks that line `converted=true` + `sale_id` on success — this is what makes partial conversion (some lines sold, others left open) fall out for free, and keeps sale-creation logic in exactly one place.

---

**WhatsApp sharing and the plan's "extras" (credit notes, service/repair GST invoices) were explicitly deferred, not built.**
Why: WhatsApp needs Meta Business verification — a 2-4 week external process requiring the owner's business documents, entirely outside what could be done in this session. Credit notes and repair-invoice support are new features, not the cleanup they were bundled with in the original plan, and weren't explicitly requested.
Impact: `document_sends.channel` already accepts `'whatsapp'` as a value (schema is ready) but no Meta integration, templates, or UI exist yet. No credit-note or repair-invoice tables/routes exist. Both are documented as open follow-ups in `docs/current-progress.md` and `docs/CHANGELOG.md` rather than silently dropped.

---

**(2026-07-23) `accessories`/`accessory_movements` retired — `sku_master` is the single catalog for every sellable item, no exceptions.**
Why: a separate `accessories` (catalog: name/quantity/cost/selling_price/`review_status`) + `accessory_movements` (quantity ledger, its own trigger) table pair had grown up alongside `sku_master`, tracking mice/chargers/bags outside the normal SKU system — with no ADR ever written explaining why. Investigation found this was never a deliberate parallel design: `sku_category_templates` already had complete spec schemas for RAM/SSD/CPU/GPU/Keyboard/Mouse since the app's original schema (months before `accessories` was created), and `sku_master` already held 4 real RAM rows from an earlier, abandoned attempt to catalog accessories the normal way. The `sync_sku_stock_from_movement` trigger that maintains `sku_master.quantity_in_stock` only ever reads `stock_movements.sku_id`/`quantity_change` — it has zero dependency on `asset_ledger` — so fungible, non-serialized items were always mechanically supported without `accessories` ever needing to exist. `purchase_order_items` already carries a plain `quantity` column, so the owner's deferred-PO-attach step needs only one line item (`quantity = N`), not per-unit asset numbers.
Impact: `accessories`/`accessory_movements` and their trigger are dropped. Every accessory (RAM/SSD/CPU/GPU/keyboard/mouse via their existing categories, anything else via a new generic `ACC` category) is a `sku_master` row like a laptop, tracked purely via `stock_movements` with no `asset_ledger` row (fungible items don't need per-unit serial/QC/warranty tracking). The `review_status`/"pending review" gate accessories had is not replaced — a new employee-created accessory SKU is immediately live and sellable, exactly like a new employee-created laptop SKU, since the employee already types the sale price directly at sale time regardless of any stored default price. See the new rule in `CLAUDE.md`'s Data model section: no category of sellable item ever gets its own parallel catalog/quantity table again — a new item type is a new `sku_category_templates` category, never a new table.

---

**(2026-07-23) Data-integrity hardening pass — duplicate-serial prevention, post-invoice correction guards, PO accessory landmine, config summary, Zoho import, correction audit trail.**
Why: an architectural review across 10 areas (full analysis in `~/.claude/plans/stateless-shimmying-pearl.md`) found several latent data-integrity gaps, some already exploitable through the live UI. The highest-risk ones were addressed in priority order.
Impact:
- **Duplicate serial numbers.** `asset_ledger.serial_number` has no DB uniqueness constraint and none of the three write paths (Stock Intake, PO Receive, Stock edit) ever checked for an existing match — a unit could silently become two rows (doubled `quantity_in_stock`, both sellable). Added `lib/duplicate-serial.ts`: a normalized cross-`source` lookup wired into all three paths as a **warn-then-confirm** (`error_code: 'duplicate_serial'` → the UI re-submits with `confirm_duplicate: true`), escalating to a **hard block for employees** when the existing row is already `sold` (`duplicate_serial_sold`). Kept soft (not a hard DB constraint) because 7 real legacy duplicate serials already exist awaiting the owner's manual reconciliation — a live unique index would need a dedup sweep first (deferred, flagged for the owner). The helper prefers a `sold` match when several rows share a serial, so severity can't be masked by row order.
- **Post-invoice correction drift.** `PATCH /api/asset-ledger/[id]/reassign-sku` and `PATCH /api/sales/[id]` (price) had no guard against editing a unit/sale that was already on a generated invoice — the invoice is a frozen snapshot and silently diverged. Both now return `error_code: 'already_invoiced'` (409) unless `confirm_despite_invoice` is passed, and both the Fix-SKU dialog and Sales Ledger surface the warning.
- **PO wizard accessory landmine.** The general PO wizard's SKU picker had no category filter, and `POST /api/purchase-orders/[id]/submit` blindly mints one `asset_ledger` row per unit of quantity for every line — so a PO for "50 chargers" would have created 50 bogus asset-numbered rows for a fungible item. Fixed both ends: the picker now excludes non-serialized categories (`exclude_category` param on `/api/sku-master`), and `submit` rejects any quantity-only SKU as a server-side backstop. Accessory purchasing stays on the dedicated `from-accessory-stock` deferred-PO flow.
- **`repair_job_parts` rebuilt.** It still referenced the dropped `accessories`/`accessory_movements` tables (0 rows, dead). Repointed `accessory_id` → `sku_master(id)`, dropped `accessory_movement_id`, added `stock_movement_id`. `POST /api/repair-jobs` now accepts a `parts` array, validates stock up front (oversell-guarded), writes a `stock_movements` `'sale'` per part, and links the `repair_job_parts` row to it. Surfaced as a "Parts Used" picker on the Service form.
- **Also fixed a live regression** from the earlier accessories consolidation: `lib/invoice-finalize.ts` still queried the dropped `accessories` table, which would have crashed invoice generation for any accessory sale — repointed to `sku_master`.
- **Configuration summary.** `sku_master.specifications` was stored but never rendered anywhere — Stock/SKU-Master lists showed only the raw `sku_description` (often "Migrated item"). New pure function `lib/sku-config-summary.ts` (`buildConfigSummary`) computes a legible string ("Dell Latitude 5400 — i5 / 8GB / 256GB SSD / 14\"") from `field_schema` + `specifications`, wired into StockView, SKU Master, and the Sell unit picker. Warranty fields (already stored, never shown) now surface on the asset detail page. No schema change.
- **New `ADP` (Adapter/Charger) category** (`sku_category_templates`): structured brand/connector_type/wattage/compatible_brand, since adapters are a real recurring product line, not one-off `ACC` free-text. Added to every accessory-category list (now `RAM,SSD,CPU,GPU,KBD,MOUSE,ACC,ADP`).
- **Accessory correction UI gaps.** Exposed the already-supported `'adjustment'` movement type as a "Correct Quantity" control, and wired `sku_master.status` (archive/reactivate — the column existed but `PUT /api/sku-master/[id]` never allowed writing it; hard-DELETE was the only removal path and failed exactly when history existed). `/api/sku-master` GET gained a `status` param (`all` to include archived).
- **"Under repair" badge.** A unit out for repair keeps its existing `asset_ledger.status` (repair-job creation never changes it), so `/api/stock` now joins open `repair_jobs` and StockView shows an "Under Repair" badge — no stored status column.
- **Zoho historical invoice import.** New `invoices.source` (`system_issued`/`imported_zoho`) + `imported_by`/`imported_at`. `POST /api/invoices/import` (owner-only) inserts an already-issued invoice with its real number preserved verbatim, **never calling `next_document_number`** — so it can never desync or collide with the live Digitalbluez counter (verified: counter untouched at 680 through the whole test run). Surfaced as an "Import Historical Invoice" screen + an "Imported" badge in the invoices list. Chose `source` over a second `external_invoice_number` column to avoid a two-numbers-per-invoice ambiguity.
- **Generalized correction audit trail.** New append-only `field_corrections` table (`table_name, record_id, field_name, old_value, new_value, changed_by, changed_at, reason`) via `lib/field-corrections.ts`, wired into the serial-edit, sale-edit, and SKU-master-edit paths — replacing silent raw UPDATEs with a logged history, same idiom as `stock_movements`/`asset_qc_checks`/`asset_cost_adjustments`.
- **Repair/replacement GST invoicing** was left deliberately unbuilt — genuinely new feature work (repair charges are already tracked on `repair_jobs`, just not GST-invoiced), pending an explicit owner decision, not a data-integrity issue.
Verified end-to-end via a disposable script (34 checks, all passing, real Supabase auth users + real HTTP calls, cleaned up and re-queried; deliberately used the Techtenth entity for all sale/finalize tests so the real Digitalbluez legal counter could never be spent). `npx tsc --noEmit` + `npm run build` both clean.

**(2026-07-24) Reversal of the PO accessory block — accessories are now first-class in the full PO → receive → Purchase-Invoice flow (category-aware, not excluded).**
Why: the 2026-07-23 "PO wizard accessory landmine" fix took the *cheap* option — it hid accessories from the PO wizard and made `submit` reject them, routing all accessory purchasing through the employee-first `from-accessory-stock` deferred-attach flow. The owner correctly pushed back: that removed the ability to **buy accessories the proper way** — start from a PO, pick the vendor there, receive against it, and create/upload a **Purchase Invoice** — the same first-class flow laptops have. Vendor was only capturable in a buried per-SKU "attach" step, and although the auto-created PO *could* technically take a PI, there was no surfaced path to it. The original bug (submit mints one `asset_ledger` row per unit of quantity, which is nonsense for a fungible item) was real, but the right fix was always to make the flow **category-aware**, not to exclude accessories — this was even flagged as the "longer-term, complete fix" in the analysis and then skipped.
Impact: new `lib/sku-categories.ts` (`NON_SERIALIZED_CATEGORIES` + `isSerializedCategory`) is the single source of the serialized/fungible split, replacing the array that had been copy-pasted into 5+ files.
- **PO wizard**: accessories are back in the SKU picker and the inline "create SKU" modal (removed the `exclude_category` filter). Vendor is chosen on the PO header exactly like laptops.
- **`submit`**: branches per line — serialized categories reserve N asset numbers + N `asset_ledger` rows (unchanged); fungible categories are a no-op at submit (nothing to reserve). No more reject.
- **`receive`**: branches per line — serialized lines take one serial per reserved asset number (unchanged); fungible lines take a **received quantity**, write one quantity-based `stock_movements` receipt (`po_id`/`po_item_id` linked), and record the purchase cost onto `sku_master.base_cost`. Partial receipts supported; the "fully received" check derives received-qty per line (serials count for serialized, summed receipt movements for fungible) — no stored counter.
- **Purchase Invoice + upload**: works **for free** once accessories flow through a normal PO — the PI screen, vendor, and invoice-file upload were always category-agnostic; they just needed a real PO to point at. No PI-side changes.
- **`hard-delete`**: stock reversal now counts fungible received-qty via summed receipt movements (was `serial_numbers.length`, i.e. 0 for accessories) so deleting a received accessory PO can't leave `quantity_in_stock` inflated.
- The employee-first "Receive Stock" quick path + `from-accessory-stock` deferred attach **stay** — both doors coexist, same two-doors/one-ledger model laptops already use (employee intake vs. formal PO).
Verified end-to-end via a disposable script (27 checks, all passing): accessory PO → submit (zero asset rows created) → partial receive → over-receive rejected → full receive (quantity + base_cost correct) → Purchase Invoice created (PO → invoiced); plus a serialized-laptop regression (2 asset rows reserved, serials received) to confirm the per-unit path is untouched; cleaned up and re-queried, `po_counter` restored. `npx tsc --noEmit` + `npm run build` clean.

**(2026-07-24) Zoho transition mode — per-entity 'external' invoicing that records Zoho numbers and disables ERP generation until cutover.**
Why: the owner keeps issuing GST invoices in Zoho for a few months while the ERP stabilises. Having the ERP *also* mint `DBI2026/27` numbers (via `next_document_number`, seeded at 680) during that window is the double-numbering confusion they asked to remove — two systems both owning one legal series. They need to record the real Zoho number on each ERP sale, and stop the ERP generating its own. Confirmed scope: **Digitalbluez (GST) only** is on Zoho; Techtenth/Cash (non-GST Bill of Supply) were never on Zoho and generate in the ERP now.

The atomic RPC `reserve_order_items(order_id, ttl_minutes)`: for a serialized item, `SELECT ... RETURNING` as the loop's own row source) so an overlapping cron run or a same-instant payment webhook can't double-act on one reservation; asset-status reverts are themselves guarded (`AND status = 'reserved_web'`) so a webhook that already flipped a unit to `sold` makes the cron's revert a harmless no-op instead of corrupting a real sale.
- **Both new RPCs are locked down correctly from the start**: Postgres grants `EXECUTE` to `PUBLIC` on new functions by default, which `get_advisors` immediately flagged. **(2026-08-01) Audit Log — cross-app activity tracking + restore, built in one pass.**

Impact: new `audit_log` table (`actor_id/email/role`, `action_type` ∈ create/update/status_change/soft_delete/restore/hard_delete/void/login/login_failed/logout, severity major/minor via a static map in `lib/audit-log.ts`, `module`, `table_name`/`record_id`/`record_label`, `field_correction_ids uuid[]` referencing `field_corrections` rows for update-type events rather than duplicating diff storage, `snapshot jsonb` for hard-delete recovery, `restore_status`). `logFieldCorrections()` now returns the inserted rows' ids (`Promise<string[]>`, was `void`) so callers can wire them into the new `logAuditEvent()` helper — its ~6 existing call sites were unaffected by this signature widening. **(2026-08-31, same day) Invoice line reconciliation removed after real-world use exposed it as unreliable; `match_skus_for_invoice_line` chased three separate false-positive/negative failure modes before that.**
Why: within the same day the owner started using it against real invoices, three distinct matching failures surfaced in sequence, each fixed and each immediately followed by the next: (1) the RPC's `%` trigram operator used Postgres's global `similarity_threshold` (0.3) against the *whole* line string — a real line like "Used Laptop Hp 1040 G8 I7 11th Gen 16/512 Touch" scored 0.19 against the correct SKU's short description and was filtered out before scoring ever ran, returning zero candidates for a unit that was plainly in stock (already sold, but still `po_id IS NULL` and therefore correctly in scope — matching was never meant to exclude sold units, since a purchase invoice can legitimately arrive after a unit already sold). Fixed by switching to `word_similarity` (matches best substring, not whole-string) with a fixed 0.2 floor instead of the GUC-tied operator. (2) Doing that alone let cross-brand and cross-model noise back in — a Lenovo SKU could out-score nothing in particular for an HP line, and "440" vs "1040" shared enough trigram/digit overlap (plus generic spec digits like "512"/"16" appearing on nearly every laptop invoice) that HP ProBook 440 G8 surfaced for an HP EliteBook 1040 G8 line. Fixed with two hard gates: the SKU's brand must appear as a whole word in the invoice text (skipped for brand-less SKUs), and if both the invoice text and the SKU's `model_name` name a 3+ digit number, they must share one. Added a category-inference gate on top (component keywords — RAM/SSD/keyboard/battery/etc — checked *before* device keywords like "laptop", since "16GB DDR4 **Laptop** RAM" uses "laptop" only as a form-factor adjective; getting this priority backwards on the first attempt returned **zero** candidates for a real RAM line, caught by testing before it shipped). (3) The digit-token extraction itself was then found to break on a real invoice's actual wording — "Probook440" (no space) doesn't tokenize as a standalone digit token under a whitespace-split approach, so the just-added model-number gate wrongly excluded the correct ProBook 440 SKU it was supposed to protect. Fixed by extracting digit runs from anywhere in the raw text (`regexp_matches(..., '[0-9]{2,}', 'g')`) instead of requiring a whitespace-delimited pure-digit token.
**A separate, more consequential bug found investigating the third case: Tier 1 (saved per-vendor template) parsing never captured line items at all — only header fields ever get a learned regex rule** (`lib/recon/pdf-text.ts`'s `deriveFieldRules` was only ever called with header field names — vendor/GSTIN/totals — never a line-item pattern; this was a documented but under-communicated limitation from the original Phase 3 build). A second, worse bug compounded it silently: an empty-lines extraction defaults every total to 0, and `validateVendorInvoiceExtraction` trivially treats `0 == 0` as a passing arithmetic check across every one of its comparisons — so a completely failed Tier 1 parse was marked `parsed`, not `needs_review`, and Invoice Reconciliation showed nothing with no error surfaced anywhere. Fixed `validate.ts` to flag `lines.length === 0` as its own issue (forces `needs_review`), and added a "Read with AI instead" fallback action to the `needs_review` banner on both recon pages (previously that banner only offered "Reviewed — this is correct," which is actively wrong to click on a zero-line extraction). The practical implication, stated plainly to the owner rather than left implicit: per-vendor templates make **vendor** reconciliation free after the first invoice, but every invoice still needs an AI read for line items — there is no free path to line-item data yet.
